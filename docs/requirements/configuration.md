# Configuration Requirements

Requirements for config file layering, field-level validation, fault isolation (malformed config), and the default text-sync mode.

> [!NOTE] Config scope
> Marksman supports three config levels: project (`.marksman.toml` at workspace root), user (`$XDG_CONFIG_HOME/marksman/config.toml` or OS equivalent), and built-in defaults. Fields are merged individually — a `None` value at one level inherits from the next.

---

## Tag: Config.Precedence.Layering

**Gist:** For every configurable field, a value set in the project config must override the same field in the user config, which must in turn override the built-in default.

**Ambition:** Predictable precedence lets workspace maintainers enforce project-level settings (e.g., a required wiki style or file extension list) that override individual user preferences. If the order were reversed, a user config could silently invalidate project settings, causing inconsistency across contributors on the same repository.

**Scale:** For each of the independently configurable fields, the fraction of test cases where the observed runtime value of the field matches the highest-priority level that specifies it, measured across all three configuration levels.

**Meter:** Integration test: start the server with a project config specifying `completion.wiki.style = "file-stem"`, a user config specifying `completion.wiki.style = "title-slug"`, and no built-in override. Invoke `textDocument/completion` at a `[[` cursor. Assert all completion items use `file-stem` slugs, confirming the project config wins.

Repeat: remove the project config; assert items now use `title-slug` slugs (user config wins).

Repeat: remove the user config; assert items use `title-slug` slugs (built-in default wins, since `title_from_heading = true` implies `title-slug` default).

Count correct observations ÷ total field-level test cases × 100.

**Fail:** Any field takes a value from a lower-priority source when a higher-priority source specifies a value for that field.

**Goal:** 100 % of observable field values reflect the highest-priority configured source.

**Stakeholders:** Repository maintainers, individual note authors.

**Owner:** Marksman contributors.

**Source:** `docs/configuration.md` — config precedence section; `Marksman/Config.fs` — `merge` / `orElse` field composition.

## Tag: Config.Validation.Candidates

**Gist:** The server must reject a configuration where `completion.candidates` is zero or negative, and must not start serving completions using an invalid candidate count.

**Ambition:** A completion cap of zero or a negative number is semantically meaningless — it would either suppress all completions or produce undefined behaviour in the truncation logic. Early validation at config load time surfaces the misconfiguration as an error before it causes a silent, hard-to-diagnose failure in a live editing session.

**Scale:** Binary: does the server treat a `completion.candidates = 0` or `completion.candidates = -1` config value as invalid, either by logging an error and falling back to the default, or by refusing to start? The requirement is that no completion response ever uses a non-positive candidate cap.

**Meter:** Integration test: write a project config with `completion.candidates = 0`. Start the server. Assert either:
(a) The server logs a config validation error and falls back to the default value (50), and `textDocument/completion` returns up to 50 candidates; or
(b) The server refuses to load the config entirely and falls back to built-in defaults.

In neither case should `textDocument/completion` return 0 candidates for a query that should match.

**Fail:** The server loads `completion.candidates = 0` silently and returns no completion items in a context where candidates exist.

**Goal:** A non-positive `completion.candidates` value is always rejected or corrected before serving any completion request.

**Stakeholders:** Wiki authors, plugin developers.

**Owner:** Marksman contributors.

**Source:** `Marksman/Config.fs` — candidates validation; `docs/configuration.md` — `completion.candidates` must be > 0.

## Tag: Config.Fault.Isolation

**Gist:** A syntactically malformed or semantically invalid config file at any level (user or project) must be dropped with a logged error; the server must continue operating using the next lower-priority config level and must not crash.

**Ambition:** Config authoring errors are common. A server that crashes when it encounters invalid TOML would be unusable in any environment where the config is managed by hand or generated by a script with a bug. Dropping the malformed level and falling back cleanly preserves server availability and gives authors actionable feedback via the error log.

**Scale:** For each config level (project, user), the binary: does the server remain running and serve requests using the fallback config when the config file at that level is invalid TOML or contains values of the wrong type?

**Meter:** Integration test (three sub-cases):
1. Project config contains invalid TOML (`key = {unclosed`). Start server. Assert server initialises without crash. Assert `workspace/symbol` returns results (server is functioning). Assert an error-level log message mentions the config file path.
2. User config contains a value of the wrong type (`completion.candidates = "not-a-number"`). Assert server initialises without crash and uses the built-in default for that field.
3. Both project and user configs are malformed. Assert server initialises with built-in defaults.

**Fail:** Server crashes, panics, or fails to initialise when any config file is malformed.

**Goal:** Server continues to operate in 100 % of cases where any config file is malformed, using the next available lower-priority config, with an error-level log entry for the dropped file.

**Stakeholders:** All Marksman users; CI and automated setup environments.

**Owner:** Marksman contributors.

**Source:** `Marksman/Config.fs` — malformed-TOML handling; `Marksman/Server.fs` — `tryLoadUserConfig` error-logging branch.

---

## Tag: Config.TextSync.Default

**Gist:** When `core.text_sync` is not set at any config level and the client does not specify a preferred sync kind, the server must default to `Full` text-document synchronisation.

**Ambition:** Incremental text sync is more efficient but is known to produce state corruption on some editors due to bugs in LSP client implementations. Full sync is the conservative safe default: it is less efficient but guarantees the server always has a consistent document text, preventing hard-to-diagnose "document out of sync" errors.

**Scale:** Binary: when `core.text_sync` is absent from all config levels and the `InitializationOptions` do not specify a preferred sync kind, is the text sync kind negotiated during `initialize` equal to `TextDocumentSyncKind.Full`?

**Meter:** Integration test: start the server with no user config, no project config, and an `initialize` request that omits `initializationOptions.preferredTextSyncKind`. Assert `initializeResult.capabilities.textDocumentSync.change = 1` (Full).

Repeat with `core.text_sync = "incremental"` in the project config. Assert `textDocumentSync.change = 2` (Incremental).

**Fail:** The server negotiates `Incremental` sync when no config or client preference specifies it.

**Goal:** `TextDocumentSyncKind.Full` is selected in 100 % of cases where no sync kind is explicitly configured or requested.

**Stakeholders:** Editor-plugin developers, all Marksman users.

**Owner:** Marksman contributors.

**Source:** `docs/configuration.md` — `core.text_sync` default; `Marksman/Server.fs` — `ServerUtil.calcTextSync` default branch (`"default", Full`); LSP 3.17 `TextDocumentSyncKind`.
